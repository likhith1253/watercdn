# arXiv paper: how to build it, learn from it and submit it

This folder is a complete arXiv submission:

| File | What it is |
|---|---|
| `main.tex` | the paper (LaTeX, `article` class, 11 pt, A4, 1-inch margins) |
| `references.bib` | 54 verified references (BibTeX). Entries marked `% UNVERIFIED` lack one field such as pages; check them |
| `main.bbl` | the compiled bibliography. **arXiv needs this file**, because it does not reliably run BibTeX itself |
| `figures/*.pdf` | vector figures, generated by `scripts/paper_figures.py` from the result files |
| `abstract.txt` | plain-text abstract for the arXiv form (no LaTeX) |
| `main.pdf` | the compiled paper, for reading only (do not upload it together with the source) |

## 1. Before anything else: fill in what only you can

1. **Authors.** In `main.tex`, replace `Firstname Lastname`, the affiliation and the e-mail. Add co-authors (a
   supervisor, for example) only if they agree.
2. **Acknowledgements.** Un-comment the block before the bibliography. Mention funding if there is any, and state
   how AI tools were used. arXiv holds the authors fully responsible for everything in the paper, and many venues now
   ask for this statement.
3. **Read every sentence and check every number** against `RESULTS.md` and `results/v2/V2_RESULTS.md`. Your name goes
   on it, so you must be able to defend each claim.
4. **Release the code.** The repository linked in "Code and data availability" must be public before you submit.
   A Zenodo DOI (see `docs/release.md`) is a nice extra.

## 3. Submit to arXiv (first time)

1. **Make an account** at arxiv.org with your institutional e-mail. An academic address makes endorsement much easier.
2. **Endorsement.** First-time submitters to a category usually need an endorsement from someone who has already
   published there. If arXiv asks for one, it shows you a code. Send that code to a professor or researcher who
   publishes in `cs.NE`.
3. **Category.**
   - Primary: **cs.NE** (Neural and Evolutionary Computing).
   - Cross-lists: **stat.ML** for the risk-control part and **eess.SY** for the water-control application. Only
     cross-list where the paper really fits.
4. **Upload.** Upload a zip of `main.tex`, `main.bbl`, `references.bib` and the `figures/` folder, with no `main.pdf`.
   arXiv compiles it; check the PDF it produces page by page.
5. **Metadata.**
   - **Title:** the same as in the paper.
   - **Abstract:** paste `abstract.txt`. The limit is 1920 characters, and this file is under it.
   - **Comments:** for example `19 pages, 8 figures, 5 tables. Code and data: https://github.com/likhith1253/watercdn`.
6. **Licence.** CC BY 4.0 is the common choice and lets anyone reuse the work with credit. The default arXiv licence
   is more restrictive. Think about where you want to publish later: almost all journals and conferences accept
   papers that already have an arXiv preprint.
7. **Timing.** Submissions made before 14:00 US Eastern time on a weekday appear the next evening. You can still
   change the submission until it is announced. After that, every change becomes a new version (v2, v3, …), and
   all versions stay public.

## 4. Before you upload: checklist

- [ ] Authors, affiliation, e-mail filled in; acknowledgements decided
- [ ] PDF compiles with no `??` (missing reference) and no `[?]` (missing citation)
- [ ] Every number in the text matches the result files
- [ ] Every `% UNVERIFIED` field in `references.bib` checked against the publisher's page
- [ ] Repository public; link works
- [ ] Figures readable when printed in black and white (they use a colour-blind-safe palette with different markers
      and line styles)
- [ ] Spell-check done. The paper uses British spelling (optimisation, behaviour) throughout; keep it consistent

## 5. How the paper is built: a guide for retyping it yourself

Write it in this order, not in reading order. The abstract and introduction are easiest to write last, once you
know exactly what you are claiming.

1. **Setup (Section 5) and Method (Section 4) first.** These are factual: what you did, with enough detail that
   someone else could redo it. Every design choice gets one reason. Keep them short and precise.
2. **Results (Section 6).** Each subsection answers one question and starts with that question's answer. Every
   number points to a figure or table. Report what went against you in the same tone as what went for you (Sections
   6.4 and 6.6 do this on purpose; reviewers trust papers that do).
3. **Problem formulation (Section 3).** Define every symbol before you use it. One equation per idea.
4. **Discussion and Conclusion (Sections 7–8).** Say what holds, what the limits are and what comes next. Do not
   repeat the results section.
5. **Related work (Section 2).** Group the papers by idea, not one paragraph per paper. End each group by saying how
   your work differs.
6. **Introduction (Section 1).** It follows a fixed arc:
   - the real-world problem;
   - why it recurs;
   - what existing methods do;
   - the question they leave open;
   - what you do;
   - the list of contributions.
7. **Abstract last.** It answers, in order: the problem, the gap, what you did, the 3–4 key numbers, the main
   limitation, and that the code is released.

**Style rules this draft follows** (they are what make writing sound human and professional):
- Use "we" and active verbs: "we built", not "a benchmark was built".
- Give one idea per sentence, and mix short and long sentences.
- Never claim "first" or "novel" without a qualifier. Here it is "to the best of our knowledge, within the
  literature we searched".
- Give each number with its uncertainty when one exists, e.g. 0.58 [0.41, 0.69].
- Avoid filler words such as "crucial", "leverage", "delve", "landscape", "robust" (unless tested), "novel" in every
  sentence, and "Moreover" at the start of every paragraph.
- Write captions that stand alone. A reader who only looks at the figures should still follow the story.

**Figure conventions.**
- Size: full text width, 2–2.5 inches tall.
- Fonts: serif at 7.5–8.5 pt, so that at print size they match the text.
- Colours: the Okabe–Ito colour-blind-safe palette. Blue marks our method, orange the baselines, grey the
  references (fresh, oracle, similarity).
- Format: vector PDF, so figures stay sharp at any zoom.
